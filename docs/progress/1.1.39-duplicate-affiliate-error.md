# 1.1.39 — "Receipt not accepted" was really a duplicate-affiliate data fault

**Status:** ✅ shipped

## Symptom
A user uploading a Bankak receipt got:

> لم يتم قبول الإيصال، يرجى التأكد من وضوح الصورة والمحاولة مجدداً

— blaming their photo. The network tab told a completely different story:

```json
{ "errors": [{ "message": "get() returned more than one PyramidAffiliate -- it returned 2!",
               "path": ["uploadAttachmentTransaction"] }],
  "data": { "uploadAttachmentTransaction": null } }
```

The same error also came back from `checkPyramidAffiliate`. Nothing was wrong
with the image. The account is linked to **two** PyramidAffiliate rows, so the
backend's `get()` raises `MultipleObjectsReturned` before it can do anything —
and no amount of re-cropping and re-uploading will ever clear it.

## Root cause
Two compounding gaps.

**1. Top-level GraphQL errors were never read.** `src/apollo/client.js` sets
`mutate: { errorPolicy: 'all' }`, so a server exception does **not** throw — it
arrives as `result.errors` with `data.<field> === null`. Every checkout call site
only inspected the payload's own `data.<field>.errors`. With `dataObj` null,
`dataObj?.errors` was `undefined`, `errorHandler` was never called, `shown === 0`,
and the code fell through to its last-resort generic message. The real reason was
sitting untouched in `result.errors` the whole time.

**2. The registration-code gate fails open on this fault — silently.**
`verifyPlatformAccess()` classified only the *missing*-affiliate dialect
("PyramidAffiliate matching query does not exist"). The duplicate dialect landed
in its "some other, unexpected error" branch, which deliberately fails **open**
(returns `true`) so a transient blip can't lock a logged-in user out. That is
still the right call here — gating the user would be the wrong remedy, they have
a code, there are simply two of them — but it meant the pre-flight gate said
"fine", an order was created, and the upload then failed. The user paid the cost
of a wrong diagnosis and an orphaned pending order.

## Fix

### `src/utils/pyramidErrors.ts` (new)
One module that knows the backend's two PyramidAffiliate error dialects, since
both are raw Django ORM exception text rather than typed codes:

- `collectErrorMessages(source)` — pulls messages out of whatever shape the fault
  arrives in: a raw string, an `Error`/`ApolloError` (including `graphQLErrors`
  and `networkError`), an array of `{ message }`, or a whole Apollo result
  (`{ errors }`). The same fault genuinely reaches us through all of these
  depending on the operation.
- `pyramidAffiliateFault(source)` → `'duplicate' | 'missing' | null`.
  `duplicate` wins when both appear — it is the one the user cannot act on.
- `notifyDuplicateAffiliate()` — the single user-facing message, so the wording
  and the error code cannot drift between the three surfaces that show it.
- `reportDuplicateAffiliate(where, source)` — classify + log + notify, returns
  `true` when handled so the caller stops.

The duplicate regex matches `/returned more than one PyramidAffiliate/i` — the
stable middle of Django's sentence, so it survives the trailing count changing
from "2" to "3" and the queryset prefix varying.

### The message
> تعذّر إتمام العملية: حسابك مرتبط بأكثر من رمز تسجيل. يرجى التواصل مع إدارة
> المركز وذكر رمز الخطأ: **DUP-AFFILIATE**

It states the cause — more than one registration code on the account, which on
its own tells the user the receipt is not the problem — and routes them to the
administration with a short code they can quote and we can grep. It deliberately
does **not** editorialise about whose fault it is. It is **sticky**
(`duration: 0` + a dismiss action) because it is not retryable — it has to
survive long enough to be read and screenshotted, unlike the 5s auto-dismiss of
a normal error.

`logger.error` also prints the raw server text with a `[DUP-AFFILIATE]` prefix.
`logger.error` always forwards, production included, so the exception is in the
console of the device that hit it.

### Wiring
- `src/stores/pyramid.ts` — new `affiliateFault` state, set by
  `verifyPlatformAccess()` from both the `errors` array and a thrown
  `ApolloError`. Still fails open on `duplicate` (unchanged, and deliberate),
  but the reason is now recoverable by callers. New `hasDuplicateAffiliate()`
  method — a method rather than a field read because TypeScript narrows a
  property at its first comparison and then reports a legitimate second check in
  the same function as dead code, even though the intervening `await` reassigns
  it. vue-tsc caught exactly that.
- `src/components/ShoppingCard/bankakPay.vue` — checked at all five exits:
  pre-flight gate, order creation (top-level errors **and** throw), the upload's
  `result.errors`, a post-upload gate re-probe, and the outer catch. The
  pre-flight check now stops before creating the order, so no orphaned pending
  order is left behind.
- `src/pages/ShoppingCart.vue`, `src/components/ShoppingCard/payment.vue` — the
  other two gate call sites, so the user is told at the top of checkout instead
  of discovering it at the receipt screen. Both previously would have routed a
  duplicate-affiliate user to the registration-code page: wrong advice, since
  they already have a code.

## Verification
Detector exercised against the **exact** payloads from the production report —
both the `checkPyramidAffiliate` and `uploadAttachmentTransaction` responses, as
a bare `errors` array and as the whole result object, plus a thrown
`ApolloError`, the `"it returned 3!"` count variant, the missing-code dialect,
an unrelated error, `undefined` and `[]`. 9/9 classified correctly.

Live in the running app: `reportDuplicateAffiliate()` fed the production payload
returns `true`, logs `[DUP-AFFILIATE] uploadAttachmentTransaction: …` with the
raw server text, and renders the toast. Confirmed it survives past 8s (a normal
danger toast dies at 5s) and that the "حسناً" action dismisses it. All three
i18n keys resolve in **ar** and **en**.

Gates: `tsc --noEmit` exit 0 · `vue-tsc` error set byte-identical to the
pre-change baseline (13) · `codegen:check` no drift · `quasar build -m spa`
succeeded.

Not exercised live end-to-end: the flow is auth-gated and behind a real payment,
so the actual receipt submission on an affected account was not replayed.

## Note
This is frontend diagnosis only — it explains the fault, it does not repair it.
The duplicate `PyramidAffiliate` row still has to be deleted server-side before
that account can check out. Every affiliate-touching operation for the user
(checkout, receipt upload, commission) keeps failing until then.
