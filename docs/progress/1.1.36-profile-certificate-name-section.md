# 1.1.36 — Profile: restore the missing certificate-name section

**Status:** ✅ shipped (confirmed live by the reporter)

## Symptom
The profile page has no way to set the name that gets printed on training
certificates. It existed before the rebrand and disappeared with it.

## Root cause
The feature was never deleted — it was **orphaned**. Everything below the UI
survived the phase-4 redesign intact:

- `src/graphql/account_management/mutation/UpdateCertificateName.js` — present
- `UpdateCertificateNameResult` / `…Variables` in `src/types/auth/types.ts` — present
- `GetMyProfileData` still selects `certificateName` + `certificateNameConfirm`
- all four Arabic i18n strings — present in both locales

Only the renderer was lost. `src/components/Profile_managements/UpdataCertificateName.vue`
still sat on disk, but a repo-wide grep found **zero** importers: the redesigned
`Profile.vue` was rebuilt with three sections (identity, personal data,
preferences) and simply never wired it back in.

This compounded the certificate-download bug from
[1.1.32](1.1.32-certificate-download-406-fix.md): the old download path
redirected users to `/profile` to set a missing `certificateName` — to a page
that had no field to set it on. That redirect is already gone (the backend is
the authority now), but the underlying gap was real.

## Fix
Restored as an inline `profile-section` in
`src/pages/account_management/Profile.vue`, between "personal data" and
"preferences", rather than by resurrecting the old component. Reasons:

1. The page's other sections are inline too — a component here would have been
   the odd one out.
2. It reuses `.profile-section`, `.profile-section__head`, `.profile-form`,
   `.profile-form__grid` and `.profile-form__actions` directly, so it matches
   the rebrand exactly with no duplicated SCSS to drift.
3. The orphan was pre-rebrand: `q-banner` + `q-input`, off-brand against the
   `ds-input` the rest of the page uses.

`UpdataCertificateName.vue` was deleted.

### Behaviour
The field is **write-once** — the backend accepts `updateCertificateName` only
while it is empty — so the UI has two distinct states rather than an edit toggle:

- **Not set:** amber callout (passport-name advice), name + confirm inputs, and
  a "تعيين" submit. Submit stays disabled until the input is non-empty, Latin,
  and matches its confirmation.
- **Already set:** the value rendered read-only with a lock note saying it
  cannot be changed. No form, no button.

Validation added over the old component, which only compared the two fields on
submit and reported failures via toast:

- Whitespace is collapsed before comparing, so `AHMED  ALI` and `AHMED ALI`
  match instead of failing a confirmation the user typed identically twice.
- Latin-letters-only check (`/^[A-Za-z][A-Za-z\s.'-]*$/`). The certificate is
  issued in English and the value is uppercased; Arabic input would render as
  mojibake on the PDF.
- Errors surface inline via `DsInput`'s `error` prop, and only after a field has
  been blurred once — no red on an untouched form.

On success it clears the inputs, refetches `GetMyProfileData`, **and** calls
`auth.getMyProfileData()` — `CertificatePage` reads `certificateName` off the
cached auth user, not off this page's query, so refreshing only the page query
would leave the certificates screen stale. The success toast carries a
"شهاداتي" action routing to `my-certificate`.

`refetchQueries` rather than an optimistic cache write: the backend normalises
what it stores, and since this value can never be corrected from the UI, the
user must see exactly what was persisted.

## Files
- `src/pages/account_management/Profile.vue` — new section, state, validation,
  `submitCertificateName()`, two SCSS blocks; added `useRouter` + `useAuthStore`.
- `src/components/Profile_managements/UpdataCertificateName.vue` — **deleted**.
- `src/i18n/{ar,en}/index.js` — 5 new keys (section subtitle, lock note, two
  validation messages, success message). The 4 pre-existing certificate strings
  were reused as-is.

## Verification
- `tsc --noEmit` exit 0.
- `vue-tsc` — no errors in `Profile.vue`; pre-existing baseline unchanged.
  Relevant because vue-tsc type-checks template bindings on `<script setup
  lang="ts">`, so every new ref/computed used in the markup is confirmed wired.
- `codegen:check` — no drift.
- `quasar build -m spa` — succeeded; the compiled `Profile-*.js` chunk contains
  `certname-heading`, `cert-name__callout`, `cert-name__locked`,
  `updateCertificateName`, `my-certificate` and the new success string.
- Both locale files parse; all 11 keys the section uses resolve in ar **and** en.
- `/profile` redirects unauthenticated users to `login?redirect=/profile` with a
  clean console.

Confirmed live by the reporter on a real logged-in account.

Remaining gap: an account that already has a `certificateName` only ever sees
the locked state, so the **set** path (callout, two inputs, validation, mutation
round-trip, set→locked transition) still wants a pass on a fresh account with an
empty `certificateName`.
