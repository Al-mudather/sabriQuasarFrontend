# 1.1.41 — VdoCipher "Error 6006": one persistent player, lite mode, resume, recovery

- **Date:** 2026-11-13
- **Status:** 🟡 partial — shipped on `master` (not pushed); traced headless and played for real on desktop Chrome with Widevine. A low-end Android phone is the one thing still to confirm (see "Not verified").
- **Commits:** `d193b7b`, `e73cc73`, `9bac1a3`, `5dde43a` (local tag `vdocipher-6006-persistent-player`, not pushed)
- **Review fixes:** `31e4844`, `8bfbc9b`, `5a27fa8`, `a091f02`, `251cdcb`

## Root cause

"Error 6006. Multiple active videos…" is Shaka Player's `FAILED_TO_GENERATE_LICENSE_REQUEST`:
the phone's Widevine stack refused to open one more DRM session. Android caps
sessions device-wide. Three facts made the classroom hit that cap:

1. A normal (non-lite) VdoCipher player opens its session when the iframe
   **loads**, not when the student presses play.
2. The player never closes that session when its iframe is removed (no
   `pagehide` handler); release is left to garbage collection. Our fixed 400 ms
   gap was therefore a hope, not a guarantee.
3. The classroom built a new iframe for every lesson, and always opened on
   lesson 1. A returning student got lesson 1's player, then the lesson they
   wanted: two sessions within seconds on every visit. Browsing four lessons
   opened and abandoned four sessions in about 4 s.

### Decisions worth knowing

- **Never-played switch rebuilds the iframe instead of calling `loadVideo`.**
  `loadVideo` always runs non-lite and autoplays, so using it for a student who
  is only browsing would open a session per lesson — the thing we are removing.
  The cost is one cheap lite document per lesson browsed (poster, `index.js`,
  one metadata call; measured below).
- **`api.js` calls `onVdoPlayerV2APIReady` before it assigns `window.VdoPlayer`.**
  Found in the real-Chrome run (the first iframe never got its API). The loader
  waits for the script's `load` event instead.
- **The stage follows the route with one deliberate lag.** Leaving a VdoCipher
  lesson for a Vimeo / self-hosted / file / quiz lesson, or leaving the
  classroom, first awaits `stopVdoCipherPlayers()`. Once Vue detaches the
  iframe there is nothing left to wait for.
- **Resume also uses a device-local hint** (`localStorage`, keyed by enrollment):
  the progress list is cached for ten minutes, so "leave and come straight
  back" would otherwise resume from a stale snapshot.

## Review round (2026-11-15)

An independent review of `d193b7b..5dde43a` found one high-severity fault and
several smaller ones. All fixed in follow-up commits (see the top of this note).

| # | Finding | Fix |
|---|---|---|
| 1 | The vendor player accepts `loadVideo` and silently does nothing when it has no playback tech (lite / never played; a second `loadVideo` while the first is initialising). We treated the resolved promise, and even a timeout, as success: lesson B's title over lesson A's video. | `loadVideo` is chosen only after a real `play` / `playing` for the current video; the flag is cleared on every `loadVideo`. A switch counts only on `emptied` **after** our call followed by `loadstart` / `loadedmetadata`. No sign within 6 s, a rejection or an error = failure → graceful teardown + rebuild with the played-gap. `loadedSrc` and the iframe title change only on that sign or on a rebuilt iframe. The focus (blur) heuristic now only picks the release gap. |
| 2 | Invalid embed followed by a valid one on the same component: spinner forever (the host element was not rendered yet). | The lesson watcher runs after render; `create()` waits for the host and reports `idle` if there is none. |
| 3 | A v2 player whose API never attached reported "no session". | Reported as unknown (`hadSession: undefined`), which the gap policy treats as a session. |
| 5 | `stop()` racing a new `show()`: two iframes for up to 450 ms, and a late `idle`. | A new iframe waits for the teardown in flight; `stop()` leaves the phase alone when a new request owns it. |
| 6 | A → B → A with a slow `EndLearningUnit(A)`: the late answer cleared the progress id of the new visit (same row). | One token per `start()`; `end()` is deduplicated per visit and clears only its own visit. Stale `Start` answers are ignored. |
| 7 | Resume: a stale local hint fell back to lesson 1; a course switch mid-resolve could push the old course with the new lesson, or block the new course; a device clock in the future made the hint win forever; no check that the lesson can be opened. | Hint anchor first, then server rows alone. Run token per course. Hints stamped more than 60 s in the future are dropped. Lessons whose payload the backend stripped are skipped. |
| 8 | `withLiteMode` on a v2 URL with no query and the credentials in the fragment added a query, which makes the player ignore the fragment. | The flag is appended to the fragment in that shape. |
| 9 | Late `arbiter.release` after an invalid lesson could drop a newer claim; "failed, then taken over by another tab" needed two taps; a BroadcastChannel was opened on pages that only report a TYPE_HASIF / Vimeo teardown. | Claim sequence guard; "play here" after a failure is a fresh attempt; the shared arbiter opens its channel on the first claim. |

**Locked lessons (item 7).** The backend has no drip or sequential lock. What it
does (`course_management/graphql/types.py`, `resolve_model_value`, read-only
check) is strip the payload of a lesson the viewer may not access — no valid
enrollment for that unit, which can happen for a unit shared from another course
(`is_unit_accessible`). A video loses `video`, `cipher_iframe` and
`video_metadata`; a file loses `attachment`. Resume treats such a lesson as not
openable: it is skipped when looking for the next unfinished lesson, and an
anchor that is not openable falls back to the server rows, then to the old
first-lesson behaviour.

**Not done:** a unit test of the `ClassroomContentView` route watcher. Mounting
that page needs the router, the classroom context and Apollo; the logic it
relies on (`end()` once per visit, stale answers ignored) is unit-tested in
`useLearningProgress.spec.ts`, and the harness measures one `EndLearningUnit`
per leave.

### Real playback (desktop Google Chrome 157, real Widevine, headed)

- Never played → next lesson: iframe rebuilt, same four requests, still no
  licence traffic; reported `hadSession: false`.
- `api.js` loaded; `VdoPlayer.getInstance(iframe)` returned `video` and `api`;
  the `error` and `statusChange` listeners registered without throwing.

- Three taps within 300 ms: one `loadVideo`, for the last lesson.
- Graceful stop: blank document loaded in under 10 ms, then removal.

## Not verified — needs a real low-end Android phone

- That 6006 actually stops. Everything about Widevine session limits on phones
  is inferred from the vendor's bundle and docs; desktop Chrome does not have
  the limit.
- That `loadVideo` releases the old session quickly enough on a slow phone, and
  that 1500 ms is enough after a played player is destroyed.
- The real 6006 payload shape (`code` vs `payload.code`); both are read.
- iOS Safari: `loadVideo` autoplay needs a user gesture there. Expected result
  is the player's own play button; not run on a device.
- `api.js` runs in our origin. This is the vendor-documented integration and was
  accepted in review: a compromise of `player.vdocipher.com` would run script in
  the student app. The repo has no Content-Security-Policy configuration anywhere (searched the whole tree: none
  in `quasar.config.js`, `index.html` or the `Dockerfile`); if one is
  added it needs `script-src https://player.vdocipher.com` and `frame-src
  https://player.vdocipher.com`.
- `api.js` can throw an uncaught `TypeError` in our page when `loadVideo` is sent
  before the player has metadata (seen on real Chrome). We only send it after a
  `play` event, which avoids the case measured; it is still vendor code.
- Sessions held by something the page cannot see (the mobile app, another
  browser, picture-in-picture). Lite mode shrinks the window; the help panel
  covers the rest.
