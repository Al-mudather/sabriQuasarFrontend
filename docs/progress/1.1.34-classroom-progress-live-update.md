# 1.1.34 — Classroom: progress updates without a page reload

**Status:** ✅ shipped (verified live by the reporter)

## Symptoms
1. **Overview panel frozen.** Finishing a video marked the lesson complete (the
   rail eventually showed a green check) but the Overview's
   `4 / 11  36%` never moved. Only a full page reload corrected it.
2. **Rail numerator stuck at 0.** A unit read `INTRODUCTION TO THE CO… 0 / 1`
   after the learner had already watched that single lesson.
3. **Rail denominator inflated.** `LESTINING SUBTEST 0 / 5` on a unit that
   expands to show only 3 videos.

## Root cause 1 — the mutation can't update what the Overview reads
`ClassroomOverviewPanel` reads `completed / total / percentage` off the
**enrollment** entity, sourced from `GetEnrollmentByCourseForCurrentUser` with
`fetchPolicy: 'cache-first'` (`useCourseBootstrap.ts:101`).

The completion mutation `src/graphql/classroom/mutation/EndLearningUnit.js`
returns only:

```graphql
endLearningUnit(...) { success  learning { pk complete } }
```

No `enrollment`, no `progress { completed total percentage }` — so Apollo has
no normalizable entity to write back to, and the cached enrollment is never
invalidated. `end()` in `useLearningProgress.ts:145` patches a **local ref**
(`localOverrides`) instead, which drives the rail tick but nothing else. Result:
`cache-first` kept serving the stale percentage until a reload (or the 10-minute
staleness TTL) re-ran the query.

`useCourseBootstrap.ts:225` already exposed a purpose-built
`refreshEnrollment()` for exactly this case — **and nothing in the codebase ever
called it.** It was dead code.

### Fix
Wire it up, frontend-only, no schema change:
- `classroomContext.ts` — added `refreshEnrollment: () => void` to the context type.
- `ClassroomLayout.vue` — destructure it from `useCourseBootstrap` and provide it.
- `ClassroomContentView.vue` — new `endProgressAndSync()` (await `end()`, then
  `refreshEnrollment()`), used at the three real lesson-boundary events:
  video-end (`onComplete`), lesson switch, and rail selection. Deliberately NOT
  on unmount — the component is going away.

Ordering is safe: `end()` awaits the mutation, so the backend has committed
before the enrollment is re-read.

## Root cause 2+3 — one bug, two symptoms
Both counters in `CurriculumRail.vue` derive from the unit's **lazily-hydrated**
lesson array, which is `[]` until that unit is expanded:

- Numerator (`completedCount`, `CurriculumRail.vue:113`) filters that empty
  array → a hard `0` for every unexpanded unit regardless of real progress.
- Denominator (`unitLessonTotal`, `CurriculumRail.vue:117`) falls back to the
  server's raw `courseunitcontentSet.totalCount`, which counts `NoneType`
  placeholder rows and content kinds `mapEdgesToContents` filters out
  (`useUnitContents.ts:69-100`). Once hydrated it switches to the real filtered
  length — which is exactly why `0 / 5` becomes `3 / 3` on expand.

This sits on top of the count quirk already documented in
[1.1.23](1.1.23-classroom-external-units-fix.md)–[1.1.25](1.1.25-classroom-units-first-render.md),
but it is not only that quirk: even with a perfect backend count, the header
would still overcount relative to what the rail renders.

### Fix
`ClassroomLayout.vue` — after the existing eager hydration of the *active* unit,
hydrate **every** unit in the bootstrap. `loadUnit` is idempotent,
in-flight-deduped and TTL-cached (`useUnitContents.ts:143-171`), so this costs
one request per unit on a cold classroom load and nothing thereafter. Collapsed
units don't render their body, so there is no skeleton flicker.

## Verification
- `vue-tsc` clean for all four touched files (the project's pre-existing error
  baseline in `courseCard.vue` / `auth.ts` / `QuizQuestion.vue` is untouched).
- `quasar build -m spa` succeeded.
- Confirmed live by the reporter: progress now updates without a reload and the
  rail counters are correct from first paint.

## Backend follow-up (optional, not required)
The cleaner long-term fix for symptom 1 is to have `EndLearningUnit` return the
updated `enrollment { progress { completed total percentage } }` so the cache
updates from the mutation payload with no extra round trip. That needs a backend
schema change; the frontend refetch above is sufficient meanwhile.
